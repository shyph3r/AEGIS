# Network Traffic Analysis with Wireshark

## Day 3 — ICMP, TCP, HTTP, UDP, and DNS

## Overview

The goal of this lab was to observe how network communication actually occurs between the Kali attacker and Ubuntu target in the AEGIS lab.

Instead of only using commands such as `ping` or opening a website, I captured the underlying packets with Wireshark and analyzed how different protocols interact.

### Lab Systems

| System | Role | Lab Interface | IP Address |
|---|---|---|---|
| Kali Linux | Attacker / Client | `eth1` | `192.168.219.10` |
| Ubuntu | Target / Server | `ens37` | `192.168.219.20` |

The systems communicate through the isolated VMware Host-only network:

```text
192.168.219.0/24
```

---

# 1. ICMP Analysis

I first analyzed the traffic generated by `ping`.

Wireshark was started on the Ubuntu target and configured to capture traffic on:

```text
ens37
```

This is the Ubuntu interface connected to the AEGIS Host-only network.

I used the following Wireshark display filter:

```text
icmp
```

From Kali, I generated four ICMP requests:

```bash
ping -c 4 192.168.219.20
```

## Observation

Wireshark captured eight ICMP packets:

```text
Kali (.10)                         Ubuntu (.20)

Echo Request #1 ─────────────────►
                ◄──────────────── Echo Reply #1

Echo Request #2 ─────────────────►
                ◄──────────────── Echo Reply #2

Echo Request #3 ─────────────────►
                ◄──────────────── Echo Reply #3

Echo Request #4 ─────────────────►
                ◄──────────────── Echo Reply #4
```

Each ping therefore generated an Echo Request and a corresponding Echo Reply.

An ICMP Echo Request contained:

```text
Source IP:       192.168.219.10
Destination IP:  192.168.219.20
ICMP Type:       8 (Echo Request)
ICMP Code:       0
TTL:             64
```

The response traveled in the opposite direction using ICMP Type 0:

```text
ICMP Type 0 = Echo Reply
```

# 2. Packet Encapsulation

Inspecting an ICMP packet in Wireshark showed multiple protocol layers:

```text
Frame
└── Ethernet II
    └── IPv4
        └── ICMP
```

Conceptually:

```text
┌────────────────────────────────────┐
│ Ethernet                           │
│                                    │
│   ┌────────────────────────────┐   │
│   │ IPv4                       │   │
│   │                            │   │
│   │   ┌────────────────────┐   │   │
│   │   │ ICMP               │   │   │
│   │   │ Echo Request       │   │   │
│   │   └────────────────────┘   │   │
│   └────────────────────────────┘   │
└────────────────────────────────────┘
```

Ethernet identifies devices on the local link using MAC addresses, while IPv4 identifies the source and destination hosts using IP addresses.

The ICMP message is carried inside the IPv4 packet, which is carried inside an Ethernet frame.

This process is called **encapsulation**.

---

# 3. TTL

The ICMP packet had:

```text
TTL = 64
```

TTL (Time To Live) prevents packets from circulating indefinitely because of routing loops.

Each router forwarding the packet decreases the TTL:

```text
64 → Router → 63
63 → Router → 62
62 → Router → 61
...
```

If TTL reaches zero, the packet is discarded.

Because Kali and Ubuntu are on the same Host-only subnet, no router is required between them.

# 4. Creating a TCP Service

To observe TCP traffic, I started a temporary HTTP server on Ubuntu:

```bash
python3 -m http.server 8000
```

The target then provided an HTTP service at:

```text
192.168.219.20:8000
```

In Wireshark, I filtered traffic using:

```text
tcp.port == 8000
```

From Kali, I accessed:

```text
http://192.168.219.20:8000
```

This generated a complete TCP connection and HTTP exchange.

---

# 5. TCP Three-Way Handshake

Before HTTP data was transmitted, Wireshark showed the TCP three-way handshake.

In this capture, Kali used ephemeral port `34376` and connected to Ubuntu port `8000`.

```text
Kali                                      Ubuntu
192.168.219.10:34376             192.168.219.20:8000

        SYN ────────────────────────────►

            ◄──────────────────── SYN, ACK

        ACK ────────────────────────────►

             CONNECTION ESTABLISHED
```

### Step 1 — SYN

Kali sent:

```text
34376 → 8000 [SYN]
```

This requested the creation of a TCP connection.

### Step 2 — SYN/ACK

Ubuntu responded:

```text
8000 → 34376 [SYN, ACK]
```

The server acknowledged Kali's request and indicated that it was ready to establish the connection.

### Step 3 — ACK

Kali responded:

```text
34376 → 8000 [ACK]
```

The TCP connection was now established.

---

# 6. Client and Server Ports

The server listened on a known port:

```text
Ubuntu
192.168.219.20:8000
```

Kali automatically selected an ephemeral client port:

```text
Kali
192.168.219.10:34376
```

The TCP communication could therefore be represented as:

```text
192.168.219.10:34376
          ↕
192.168.219.20:8000
```

This demonstrated that both sides of a TCP connection use ports.

The server typically listens on a known service port while the client operating system selects a temporary ephemeral port.

---

# 7. HTTP Request and Response

After the TCP handshake completed, Kali sent an HTTP request:

```text
GET / HTTP/1.1
```

The communication followed:

```text
Kali                                  Ubuntu

TCP connection established
              │
              ▼

GET / HTTP/1.1 ─────────────────────►

                 ◄──────── HTTP/1.0 200 OK
                           + HTML data
```

Wireshark was able to display the returned HTML because the test server used unencrypted HTTP.

The response included:

```text
HTTP/1.0 200 OK
```

`200 OK` indicated that the request was successfully processed.

---

# 8. HTTP vs TCP

This experiment demonstrated that HTTP and TCP perform different roles.

TCP provides the connection:

```text
SYN
SYN/ACK
ACK
```

HTTP then sends application data through that connection:

```text
GET /
HTTP 200 OK
```

The protocol stack can be represented as:

```text
HTTP
 ↓
TCP
 ↓
IPv4
 ↓
Ethernet
```

HTTP is an application-layer protocol, while TCP is a transport-layer protocol.

---

# 9. Closing the TCP Connection

After the HTTP communication completed, Wireshark showed TCP packets containing:

```text
FIN, ACK
```

These packets were used to terminate the connection.

The observed connection therefore followed the general lifecycle:

```text
TCP Handshake
     ↓
Connection Established
     ↓
HTTP Request
     ↓
HTTP Response
     ↓
TCP Connection Termination
```

# 10. UDP and DNS

DNS (Domain Name System) translates domain names into IP addresses.

Conceptually:

```text
example.com
     │
     ▼
DNS Query
     │
     ▼
DNS Resolver
     │
     ▼
DNS Response
     │
     ▼
IP Address
```

Traditional DNS queries commonly use UDP destination port `53`.

Unlike TCP, UDP does not perform a three-way handshake before transmitting data.

A simplified DNS exchange looks like:

```text
Client                              DNS Resolver

DNS Query
example.com? ─────────────────────►

             ◄──────────────────── DNS Response
                                   IP address
```

The protocol stack for a traditional UDP DNS query can be represented as:

```text
DNS
 ↓
UDP
 ↓
IP
 ↓
Ethernet
```

This contrasts with the HTTP experiment:

```text
HTTP                       DNS
 ↓                          ↓
TCP                        UDP
 ↓                          ↓
IP                         IP
 ↓                          ↓
Ethernet                   Ethernet
```

# 11. Wireshark Filters Used

During the lab, I practiced several display filters.

### ICMP traffic

```text
icmp
```

### TCP port 8000

```text
tcp.port == 8000
```

### TCP SYN packets

```text
tcp.flags.syn == 1
```

### HTTP traffic

```text
http
```

### Traffic involving the Kali attacker

```text
ip.addr == 192.168.219.10
```

### Traffic involving the Ubuntu HTTP server

```text
ip.addr == 192.168.219.20 && tcp.port == 8000
```

These filters make it possible to isolate relevant packets from much larger network captures.

# 12. Security Relevance

Packet analysis is useful in both offensive and defensive security.

A network packet can reveal information such as:

```text
Source
Destination
Protocol
Port
Connection state
Application behavior
Timing
```

For example:

```text
Single TCP SYN
        ↓
Could be normal connection activity

Many SYN packets
to many ports
in a short period
        ↓
Could indicate reconnaissance / port scanning
```

This distinction will become important later in AEGIS when attack traffic generated from Kali is monitored using network security tools.

# Key Takeaways

This lab connected several concepts from the previous AEGIS exercises:

```text
Application
     ↓
HTTP / DNS
     ↓
TCP / UDP
     ↓
IP
     ↓
Ethernet
     ↓
Network Interface
     ↓
Network
```

I observed that:

- ICMP Echo Request and Echo Reply are the packets behind `ping`.
- Ethernet frames use MAC addresses on the local network.
- IPv4 packets contain source and destination IP addresses.
- TTL prevents packets from circulating indefinitely.
- TCP establishes a connection using SYN → SYN/ACK → ACK.
- Servers listen on ports while clients can use temporary ephemeral ports.
- HTTP application data is transmitted over a TCP connection.
- Unencrypted HTTP traffic can be inspected directly in Wireshark.
- UDP does not require a TCP-style connection handshake.
- DNS resolves domain names into IP addresses and traditional DNS queries commonly use UDP port 53.
- Wireshark filters can isolate specific protocols, hosts, and ports.

The most important mental model from this lab is:

```text
Application activity
        ↓
Transport protocol
        ↓
IP packet
        ↓
Ethernet frame
        ↓
Network traffic
        ↓
Observable telemetry
```

Understanding this relationship provides the foundation for later reconnaissance, network detection, and SOC analysis in AEGIS.
